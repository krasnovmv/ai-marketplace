# Design

## Context

Проект пока содержит README, инструкции агентов и план OpenSpec; приложения нет. Этот план уточнён после обсуждения: нужен личный каталог-зеркало для Claude Desktop и ChatGPT desktop, без исправления чужих навыков. Состав и границы описаны в [proposal.md](proposal.md).

Подтверждённый стартовый набор:

| Источник | Пакет в upstream marketplace | Путь пакета | Выбор |
|---|---|---|---|
| [DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail) | ponytail | `./` | all |
| [mattpocock/skills](https://github.com/mattpocock/skills) | mattpocock-skills | `./` | all |

Источником поставки служит upstream Git, а не локальный кеш установленного плагина. OpenSpec исключён из зеркала по решению пользователя; использование OpenSpec для ведения этих документов сохраняется.

## Goals / Non-Goals

**Goals:** точная копия выбранных пакетов; одна конфигурация; ежедневный PR при изменении содержимого; одна ручная операция принятия обновления; каталоги для обоих приложений; сохранность пользовательской рабочей папки.

**Non-Goals:** исправление или переписывание навыков, проверка качества промптов, конвертация hooks/MCP, собственная упаковка OpenSpec, сервер, база данных, автоматическое слияние PR и прямая запись в кеши приложений.

## Decisions

### 1. Минимальный стек

Node.js 22+, ESM JavaScript, pnpm и системный Git — предложение из исходного описания. JSON, файлы, хеши, subprocess и проверки покрываются стандартной библиотекой; дополнительные runtime-зависимости не закладываются. Четыре команды разделяют один конвейер подготовки результата. Git вызывается массивом аргументов без shell.

Windows/Linux нужны для локальных команд и приёмки настольных клиентов; CI-синхронизация работает на Linux. Перед первой реализацией уточнить ограничения окружения согласно AGENTS.md; это не задача по выбору новой архитектуры.

### 2. Выбор целых маркетплейсов и отдельных пакетов

В `config/upstreams.json` находятся `marketplace: { name, owner: { name } }`, `sources` и необязательные `limits`. Источник задаёт `id`, `type`, `repository`, `branch`, `enabled` и `selection`.

- `marketplace + all`: все записи manifest, необязательный `exclude: [name]` для явных исключений.
- `marketplace + selected`: `plugins: [{ name, enabled }]`.
- `repository + selected`: `plugins: [{ name, path, enabled }]`.

Автоматического порога «маленький/большой» нет. Для ponytail и mattpocock начальное значение — all. Ветки фиксируются в config после проверки upstream при реализации; генератор не угадывает их каждый запуск. Внутри выбранного пакета сохраняются все навыки и новые файлы. Новая запись marketplace автоматически входит только в all, причём сначала в PR.

All означает все плагины, перечисленные в manifest, а не поиск любых папок в репозитории. Начальный входной формат — `.claude-plugin/marketplace.json` с локальными строковыми source. Неподдерживаемый source, недопустимый файл или коллизия блокируют весь запуск. Пользователь может явно исключить запись или выбрать selected. Алиасы и автоматическое переименование не нужны стартовому набору.

Исчезновение ранее принятого пакета и изменение его пути остаются блокирующими ошибками. Для удаления пользователь меняет config; для подтверждённого переноса может явно перейти на repository с новым path. Новые пакеты в all не дают права молча удалять старые.

### 3. Точное и безопасное копирование

Разрешить branch один раз, затем читать Git tree/blobs конкретного SHA во временном каталоге. Это сохраняет байты без checkout-фильтров и исключает исполнение upstream hooks. Не запускать build, install или скрипты пакета.

Копируются все обычные отслеживаемые файлы выбранного дерева. Нет широкого списка исключений по именам `dist`, `node_modules`, `.github`: удаление таких файлов нарушило бы зеркало. Вложенные workflow-файлы остаются внутри `plugins/<name>/` и не переносятся в корневую `.github/workflows/`. Git-служебные данные и локальные cache-файлы не попадают в поставку.

Сохраняются manifest, инструкции, hooks, ресурсы, лицензии и Git executable mode. Права на Windows учитываются через Git mode, а не только filesystem permissions. Проверяются безопасные относительные пути, переносимые имена, коллизии регистра, ссылки и специальные файлы. Submodules и LFS-указатели отклоняются вместо загрузки зависимостей.

Сохраняются базовые пределы 5 МиБ на файл и 20 МиБ на пакет, настраиваемые в config, и отказ для исполняемых бинарников. Если пакет не проходит проверку, он не обрезается и не чинится. Ограничения совместимости функций не приравниваются к ошибкам безопасного копирования.

### 4. Отдельная копия вместо восстановления рабочей папки

Конвейер: config → SHA → выбор пакетов → чтение и проверка → хеши → metadata → два каталога → проверка целого результата → diff.

`sync` готовит результат в отдельной временной копии репозитория и выводит её путь. Локально база берётся из текущего Git HEAD, желаемый config читается из рабочей папки; незакоммиченные правки остальных файлов не переносятся в кандидат и не меняются. Если исходный принятый набор повреждён, проверка прекращает запуск. CI использует доверенную default branch и её config.

Результат обновляет только принадлежащие зеркалу пути: зарегистрированные в metadata пакеты, metadata и два manifest. Занятый неизвестным файлом путь — ошибка. Кандидат нельзя публиковать до успеха всех проверок. При сбое рабочая папка и удалённые ветки неизменны; неуспешную временную копию можно удалить и пересоздать.

Постоянный журнал восстановления, резервные копии и локальные блокировки замены дерева больше не нужны. Атомарность публикации обеспечивает Git commit проверенного набора; конкурентные CI-запуски сериализуются. `diff` и `sync --dry-run` используют тот же конвейер, но удаляют временный результат. `generate` явно меняет только локальные каталоги и не делает сетевых запросов.

### 5. Метаданные без шума от upstream SHA

`metadata/<name>.json` хранит идентичность принятого источника, полный SHA принятой копии и contentHash. Upstream-версия пакета не повышается агрегатором.

Хеш включает отсортированные относительные POSIX-пути, Git mode и байты файлов в однозначном представлении с длинами полей. mtime и текущее время не входят. Изменение SKILL.md, manifest, ресурсов или executable mode считается изменением пакета, даже если upstream не повысил version.

Если хеш и настроенное происхождение не изменились, прежний файл metadata сохраняется целиком. Проверенный новый SHA и время проверки выводятся в лог. Один источник может поэтому иметь разные принятые SHA у двух пакетов: обновляется только изменившийся пакет. Это осознанная фиксация принятой копии, а не последнего просмотренного коммита.

Для воспроизводимости входом служит и предыдущее принятое состояние. Явное изменение repository/path/branch пользователем отражается в новой metadata даже при совпавших байтах: это изменение конфигурации происхождения, не фоновое обновление ради SHA. Описания в выходных каталогах берутся из принятых файлов пакета; изменение описания только во внешнем marketplace не создаёт отдельный PR.

### 6. Два каталога и реальное обновление клиентов

Генерируются два небольших JSON-каталога с одним набором локальных файлов:

- `.claude-plugin/marketplace.json`: локальные source вида `./plugins/<name>`, идентичность и владелец каталога.
- `.agents/plugins/marketplace.json`: source вида `{ "source": "local", "path": "./plugins/<name>" }`, имя и отображаемое название каталога.

Оба относительных пути отсчитываются от корня marketplace, не от папки manifest. Исходные plugin manifest не переписываются; если клиент не может установить пакет, это ограничение выявляется при приёмке и сообщается явно. Не добавляется недоказанный флаг «совместим со всеми клиентами».

[Claude документирует личные marketplace из GitHub](https://support.claude.com/en/articles/13837440-use-plugins-in-claude). [OpenAI описывает локальные marketplace для Work/Codex в ChatGPT desktop](https://developers.openai.com/plugins/build/plugins#how-local-marketplaces-work), включая кеш установленной копии. Документы проверены при обсуждении 21 сентября 2026 года; поддержка конкретной версии приложения подтверждается приёмкой.

Приёмка состоит из двух отдельных операций в каждом приложении: первая установка ponytail/mattpocock из зеркала и получение изменённых файлов после merge PR. Второй тест проводится также без изменения upstream version. Используется штатное обновление, перезапуск или поддерживаемая переустановка; конкретные действия записываются в README после проверки. Автоматическое обновление обоих клиентов не обещается, а их кеши напрямую не редактируются.

### 7. Автоматизация и изменение конфигурации

Обычный путь: один раз подключить зеркало → бот проверяет источники ежедневно в 04:00 UTC → один PR из `bot/plugin-sync` → пользователь проверяет и принимает → клиент получает принятую копию штатным способом. Локальный компьютер не нужен для регулярного fetch/push.

Два workflow:

- `validate.yml` проверяет PR без upstream-сети и секретов записи. Проверяет config, целостность уже опубликованного набора, регенерацию обоих каталогов и отсутствие diff, включая untracked-файлы.
- `sync.yml` запускается по расписанию, вручную и после изменения upstreams.json в default branch; строит кандидат, проверяет и публикует только управляемые выходные файлы.

Config задаёт желаемое состояние; metadata и каталоги — опубликованное. Поэтому PR с добавлением/выключением источника или изменением selection проходит без ручного vendoring. После его merge бот отдельно предлагает изменение зеркала. До merge bot PR опубликованный каталог остаётся прежним. Изменение имени/владельца самого каталога требует регенерации его двух файлов в том же конфигурационном PR; `pnpm generate` выполняет это без сети.

Все проверки кандидата должны пройти до первого push. Concurrency исключает два одновременных writer; перед push проверяются база default branch и ожидаемый head bot-ветки. Чужие коммиты не перезаписываются. PR от бота также должен получать required checks: при реализации проверить поведение выбранного GitHub-токена и обеспечить запуск проверки bot-ветки, не полагаясь на событие, которое токен может подавить.

При отсутствии изменений новый commit/PR не создаётся; устаревший bot PR закрывается лишь после успешного полного сравнения. Ошибка оставляет существующий PR неизменным. Внешним PR не передаются write-секреты, upstream-код не исполняется. Версии CI actions фиксируются на проверенные ревизии при реализации.

## Risks / Trade-offs

- Пакет может быть непригоден для части функций клиента → сохранять его без починки, документировать результат проверки установки и ограничения.
- Клиент может сохранить старый кеш при прежней plugin version → тестировать обновление отдельно; документировать штатное действие, не подменять исходную версию.
- Режим all включает будущие пакеты → изменения проходят проверки и ручной PR; ошибки одного пакета блокируют общий результат.
- Исчезновение или коллизия требуют вмешательства → понятный отчёт и явные exclude/selected; молчаливого удаления нет.
- Полная копия может превысить лимит → конфигурируемые пределы, ошибка целого пакета вместо незаметного усечения.
- Между config PR и bot PR возможна задержка → опубликованный набор остаётся целым, workflow запускается после изменения config.

## Migration Plan

Миграции существующего приложения нет. Сначала реализовать и проверить конвейер на тестовых Git-репозиториях, затем получить реальные ponytail/mattpocock, проверить лимиты и структуру. Выполнить ручной sync workflow, принять первый PR, подключить каталог в обоих приложениях и проверить обновление установленной копии. После приёмки включить расписание. Откат принятого набора — revert его Git commit; до следующего принятия PR клиенты не получают автоматически откатившиеся upstream-изменения. OpenSpec в каталог не добавлять.
